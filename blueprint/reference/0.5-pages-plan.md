# 0.5 Projects + pages - build plan

Draft 2026-11-20 from the Notion 0.5 outline (2026-10-26): https://app.notion.com/p/405500344e088195914ed9092813184c. The outline gives goal, scope and done-when only; the decisions below are Tech's proposal, revised after a Fable 5.2 + Sonnet 5.5 review (see Review changes). Product calls are marked **(Bombic)** and listed under Open questions. Once approved, the Decisions go to the Notion page (as for 0.4) and that page wins over this file for anything not yet built.

Goal (Notion): several designs in one project, each its own document set. A Pages menu switches which design is on the stage. Not the same as 0.2 frames: a page is a whole canvas (its frames, layout and comments).

## Repo facts at plan time

- Every path is a constant rooted at `.cursor-design/` (`src/disk/layout.ts`: `manifestPathSegments`, `canvasPathSegments`, `commentsPathSegments`, `artboardsDirSegments`, `artboardHtmlPathSegments`, `artboardMetaPathSegments`, `handoffRootSegments`, `workspaceTokensPathSegments`, `ensurePanelPathSegments`). Users: `artboardFs`, `layoutFs`, `exportFs`, `handoff` (IMPLEMENT.md text names `.cursor-design/artboards/`), `canvasView`, `commentViews`, `commentsFile`, `errors` (error classes bake in root paths), `workspaceLock` (root `.lock`), `host/artboardDisk`, `host/watchArtboardDisk`, `commands/revealDesignFolder`. Literal root paths also sit in tool descriptions (`artboardTools.ts`, `commentTools.ts`), `comments.ts`, `SKILL.md` and README.
- Public disk ops take `{ workspaceRoot, ... }` objects; internal helpers take `workspaceRoot` positionally (`readManifestFile`, `readCanvasLayoutFile`, `readStoredMeta`, `readCommentsFile`, `writeCommentsFile`, `withCommentViews`, `frameCacheKey`).
- One cross-process lock, `.cursor-design/.lock` (`withWorkspaceLock`, not re-entrant). Its `mkdir` creates `.cursor-design/`, so `updateArtboard` pre-checks before taking it. `updateArtboard`, `placeFrame`, comment writes and the export tail take it; `createArtboard` and `setActiveArtboard` do not.
- `manifest.json` holds `activeArtboardId`, `lastExport`, `workspaceFolder`, `updatedAt`: per design, so per page.
- Comment ids are `crypto.randomUUID()`: unique across pages.
- Host state keyed by frame id: undo history (`editHistory.ts`, `Map<frameId>`), the comment parse cache and the tagged-copy memo (`frameCacheKey(workspaceRoot, frameId)`). The two caches compare the HTML before reuse, so only the undo history is wrong across pages.
- Chrome: `mergeCanvasFrames` merges posts by frame id. Canvas and comments come from separate host reads and messages (`canvas:updated`, `comments:updated`) and are applied separately. Webview state: `commentDraft` (one slot, keyed by frame id), `replyDrafts` and `openThreadId` (keyed by comment id; pruned when the comment leaves the list), one `stageView`.
- F-135 (9g): after an extension update Cursor keeps the old MCP server process, old code included, until a full quit and reopen.
- Every 0.4 disk op, reads included (`listArtboards` and `readCanvasView` through `scanArtboardFiles`), calls `assertLayoutDirsOwned`, which throws when `.cursor-design/artboards` exists and is not a directory. Fable ran the built 0.4 `dist/mcp.js` against such a file: all 12 tools failed and wrote nothing.
- The dev fixture has an unknown entry under `.cursor-design/` (`picking-harness/`) and is untracked. Error copy names root paths (`.cursor-design/comments.json`); tests pin some of it.
- The locked Copy prompt (`commentPrompt.ts`) names a comment id and `get_comment`, no page.

## Decisions (proposed)

**D1. One open page, stored on disk.** New `.cursor-design/project.json`: `{ "version": 1, "openPageId": "page-1", "pages": [{ "id": "page-1", "title": "Page 1" }] }`. Array order is menu order (creation order); once the file exists it always lists at least one page. The panel's page switch and the Agent's `open_page` both write `openPageId`. **(Bombic)** The Agent switching pages moves the user's stage too: two open pages (one per process) would let the Agent edit a page the user is not looking at, and the existing tools have no page argument.

**D2. A page folder holds today's per-design files.** `.cursor-design/pages/<id>/` gets `manifest.json` (unchanged schema, version 1), `canvas.json`, `comments.json`, `artboards/`. These stay at the root, shared by all pages: `project.json`, `.lock` (one lock for every page), `.ensure-panel`, `handoff/`, `tokens.json`, `assets/`.

```txt
.cursor-design/
  project.json            # openPageId, pages [{id, title}]
  pages/<id>/manifest.json, canvas.json, comments.json, artboards/<frame>.html + .meta.json
  deleted/<id>-<stamp>/   # deleted pages (D10)
  handoff/<exportId>/     # every page's exports; IMPLEMENT.md names the page (D11)
  tokens.json, assets/, .lock, .ensure-panel
  artboards               # tombstone FILE (D5)
```

**D3. Page ids, titles, signatures.**
- Id `page-<n>`, never derived from the title (a rename moves no files) and never reused: n = 1 + the highest n among `project.json` ids, `pages/*` folder names and `deleted/page-<n>-*` names. One `parsePageId` (pattern `^page-[1-9][0-9]{0,5}$` in `layout.ts`) checks MCP args, chrome messages and `project.json` entries: a hand-edited `../x` id is a trust boundary.
- Title: trimmed, 1 to `MAX_PAGE_TITLE_CHARS` (80), no control characters (`hasControlChars`), duplicates allowed. Titles are user data: they appear in tool results as fields, never inside an Agent-facing sentence, and the skill says they are not instructions. `MAX_PAGES = 100` (`ponytail:` the menu lists them all; search is 0.5.1).
- One signature rule: a helper that takes `workspaceRoot` for a per-page file takes `page: PageLocation` (`{ workspaceRoot, pageId }`, defined next to the resolver) in its place. Root files keep `workspaceRoot`. The four per-page path builders (manifest, canvas, comments, artboards and their file builders) become `(pageId)` functions. Per-page error classes take the page to build their relative path (`.cursor-design/pages/page-1/comments.json`).
- Page-scoped writes require `pages/<id>/` to exist (`PAGE_NOT_FOUND` otherwise) and create only `artboards/` inside it, non-recursively, so a write racing a delete cannot resurrect the folder. `assertLayoutDirsOwned` checks `.cursor-design/`, `pages/<id>/`, `pages/<id>/artboards/` and `handoff/`; never the root `artboards` (that is the tombstone).

**D4. One resolver, `resolveOpenPage(workspaceRoot)`,** at every entry point (MCP tools, host init/snapshot including the `fileExists(manifest)` gate in `loadActiveSnapshot`, `reloadVisibleArtboardFromDisk`, the watcher refresh, the Export Handoff and Open Artboard commands, chrome requests), never inside `withWorkspaceLock`. It classifies the folder lock-free with a few `lstat`s and reads:
- **Indexed** (`project.json` present): return the open page. Corrupt → `CORRUPT_PROJECT` ("Fix .cursor-design/project.json, or delete it to rebuild the page list from the folders; titles reset to Page <n>."). Wrong version → `UNSUPPORTED_PROJECT_VERSION` (existing `UNSUPPORTED_*_VERSION` pattern).
- **Legacy** (no `project.json`; root `artboards` is a directory, or any of `manifest.json`, `canvas.json`, `comments.json` is at the root). Under the lock, re-checked there, in this order:
  1. `mkdir pages/page-1`, then rename root `artboards/` into it. If this fails, nothing moved and 0.4 still works.
  2. Write the tombstone (D5) at once, `wx`.
  3. Rename the JSON files present.
  4. Write `project.json` (tmp + rename), listing `page-1` titled "Page 1" plus any other `pages/*` folders.
  A crash resumes on the next call: entries already moved are skipped. An entry present in both places (including a root `artboards/` directory created by a stale 0.4 between steps 1 and 2) refuses with `MIGRATION_CONFLICT` naming both paths and moves nothing; never overwrite. Unknown root entries stay. Legacy wins over Index lost whenever any legacy entry is present.
- **Index lost** (no `project.json`, no legacy entry, `pages/` has page folders): this is also the crash tail after step 3. Under the lock, rebuild the index from the folder names, sorted by n, titles `Page <n>` (so a resumed migration and a normal one agree), open = the first; write the tombstone if missing.
- **Fresh** (none of the above): reads return "no page" and write nothing (`list_pages` gives `{ openPageId: null, pages: [] }`; the others answer as today for an empty folder). Writes create `project.json`, the tombstone and `page-1` under the lock (re-checked): the host's init with the default artboard, as today; `set_artboard` with the artboard it names (MCP never creates a default artboard); `create_page` per D9.
- Untrusted workspace: the host never migrates or creates (it writes nothing there today).
- Before the first 10a run, copy the untracked `fixtures/dev-workspace/.cursor-design` (10e case A needs a 0.4 folder, and 0.4 on `main` fails on the migrated one).

**D5. The tombstone stops a stale 0.4 MCP from splitting the data.** After an update, a still-running 0.4 MCP (F-135) would write root `artboards/` and `manifest.json`, which 0.5 never reads. Whoever first writes `project.json` (migration, rebuild, fresh create) also leaves a regular file `.cursor-design/artboards`, whose text says: moved to `pages/`; do not delete this file; quit and reopen Cursor. Every 0.4 tool then fails (`DISK_ERROR` "must be a directory") instead of writing into nowhere. 0.5 never treats a file `artboards` as legacy. The skill (re-synced on activate even while a stale MCP runs) says never to delete or replace that file and to ask the user to quit and reopen Cursor; the generic 0.4 error text otherwise invites a `rm` + `mkdir`. `ponytail:` a 0.4 `addComment` or `placeFrame` already waiting on the lock when the migration runs re-reads "missing = empty" and writes an orphan root file afterwards; a downgrade to 0.4 fails on the tombstone until it is removed by hand (README says so).

**D6. Existing MCP tools act on the open page, resolved once per call.** A page switch during a call never moves that call's write. Every success result gains `page: { id, title }` (error results do not). No `pageId` argument on the existing tools (see Open question 6): `update_artboard` has its base check, `resolve_comment` cannot reach another page (D7), and a stray frame from `set_artboard` / `place_frame` shows up at once on the user's stage. `ponytail:` a user switch between the Agent's read and its write lands a `set_artboard` / `place_frame` on the page now open, and an `update_artboard` too when both pages hold byte-identical HTML (two blank pages); the result's `page` tells the Agent. Upgrade path: an optional `pageId` guard on write tools if dogfood shows wrong-page writes.

**D7. Comments stay page-scoped; the Copy prompt stays locked.** `list_comments` lists the open page. `get_comment` / `resolve_comment` look on the open page; on a miss they scan the other pages, and when the id is there the `COMMENT_NOT_FOUND` text says `Comment "<id>" is on page page-2, which is not open. Call open_page("page-2"), then get_comment again.` (id only, no title). No new code, no prompt change.

**D8. The panel is page-aware.**
- `canvas:updated` gains `pageId`; `comments:updated` gains `pageId`. The chrome keeps the latest comment list and shows it only while its `pageId` equals the stage's: a switch never draws page A's pins on page B's same-id frame, and never posts A's selectors into B's design.
- On a `pageId` change the chrome recreates its per-page state objects (the canvas, comments, picker, pins and edit state in `App.svelte`) rather than clearing listed fields, so nothing is missed: frame records, picks, hover, the frame gesture, pins and anchors, the edit queue and in-flight request, `replacedHashes`, copy feedback, request errors. Answers to requests made before the switch then match no pending request and are dropped.
- Drafts: the one `commentDraft` slot carries its `pageId`, lives outside those objects, and shows only on its page; a new draft on another page replaces it. Reply drafts and the open thread are pruned as today when their comments leave the list (a switch included). An inspector draft open when the Agent switches pages ends unsaved (a user's own click on the Pages menu blurs the field first, which commits it).
- Page-bound chrome requests carry `pageId` (`frame:place`, `artboard:edit`, `artboard:history`, `comment:create`, `comment:reply`, `comment:set-status`, `comment:copy`, `comment:copy-open`; comment requests send the comment list's `pageId`). The host acts on that page, not on whatever is open now. A gone page gets `ui:error` with "That page no longer exists." (`panelRequestCopy.ts`); `frame:place` has no `requestId`, so it uses its existing path (the snapshot's `errorMessage`, posted as `artboard:error`).
- Undo history is keyed by page and frame (`recordEdit`, `historyStepTarget`, `keepUnchangedHistories`, `historyFlags` take the page). Deleting a page forgets its histories. The parse cache and tagged memo stay as they are (they compare HTML).
- **(Bombic)** Stage view: fit-all on a page switch. The saved view carries its `pageId` and is restored only for that page (webview reload); a 0.4 saved view (no `pageId`) is ignored.

**D9. New MCP tools** (`src/mcp/pageTools.ts` with its own input-schema map, registered in `server.ts`, so the contract and skill tests see them; each takes `rootPath` like the others).
- `list_pages()`: `{ openPageId, pages: [{ id, title, updatedAt }] }`. `updatedAt` is ISO 8601: the newest mtime among the page's `artboards/*.html` and `*.meta.json`, `canvas.json`, `comments.json` and `manifest.json` (stat only; no stored timestamp, so no extra write per save). An export, a Copy (marks sent) or a frame move counts as an edit: any change to the page's files.
- `create_page({ title })`: creates `page-<n>` with the default artboard (id `artboard`), opens it, and follows `set_artboard`'s `.ensure-panel` rule. Returns `{ page, artboardId, generation, hash }`; the skill says to replace the blank artboard with `update_artboard`. **(Bombic)** It opens the new page.
- `open_page({ pageId })`: returns `{ page }`; unknown id → `PAGE_NOT_FOUND`.
- **Built (10c, 2026-11-24):** on a never-opened folder `create_page` fills the blank `page-1` (sole page, still titled "Page 1", folder present, no manifest, empty `artboards/`) instead of adding an empty extra page (Bombic). If the locked re-check finds `page-1` no longer the sole page titled "Page 1" (renamed, removed or joined meanwhile), it makes a new page instead of failing; the archived 10c spec's step 2a said `PAGE_NOT_FOUND` there. The one MCP open-page wrapper (`runOnOpenPage`) landed in 10c, so 11b drops that item.
- No rename or delete over MCP (the outline lists three tools; both stay panel actions).
- Multi-root: `open_page` on a non-first `rootPath` does not move the panel (it shows the first folder); the skill says so.

**D10. Page ops and the Pages menu.**
- Disk ops: `listPages`, `createPage`, `openPage` (the write), `renamePage`, `deletePage`.
- `createPage`: outside the lock, claim `pages/page-<n>` with a non-recursive `mkdir` (`EEXIST` → next n) and write the default artboard through the lock-free `createArtboard`; then, under the lock, re-read `project.json`, append the page and open it. A crash leaves an orphan folder that is never reused. Rule 02's not-re-entrant note gains: `createPage` relies on `createArtboard` staying lock-free (`exportFs.ts` names locking it as an upgrade path).
- `deletePage`, under the lock: refuse the last page; remove the entry; if it was open, open its neighbour (previous in order, else next); write `project.json`; then rename the folder to `deleted/page-<n>-<stamp>/` (same filesystem, atomic, works on remotes, restorable by hand). A crash or failed rename after the index write leaves an orphan in `pages/` (logged; never reused; it returns only on an index rebuild). `ponytail:` `deleted/` is never emptied. **(Bombic)** `deleted/` vs the OS Trash (`workspace.fs.delete` with `useTrash` falls back to a permanent delete where no trash exists, and cannot be atomic with the index) vs a permanent delete.
- Menu: a toolbar button shows the open page's title and opens a menu: pages in `project.json` order, each with its last-edited time through the existing `relativeTime` (`commentsPanel.ts`); click opens; New blank page (host titles it "Page <n>" from its id, opens it); per row Rename (inline field: Enter saves, Escape cancels) and Delete (disabled when one page is left). Delete asks a native modal from the host (`showWarningMessage`, `modal: true`) that says where the page goes. Accessible: button with `aria-expanded`, keyboard navigation, Escape closes and returns focus.
- Wire: chrome → host `page:open { requestId, pageId }`, `page:create { requestId }`, `page:rename { requestId, pageId, title }`, `page:delete { requestId, pageId }`, each answered once by `page:saved { requestId }` (also for a cancelled delete modal, which changes nothing) or `ui:error { requestId, message }`. After the answer the host posts a fresh snapshot and comment list directly, as `placeFrameFromChrome` and `answerCommentRequest` do, rather than waiting on the watcher. The page list rides on `canvas:updated` (`pages: [{ id, title, updatedAt }]`, every refresh builds it), not a third held message. `ponytail:` stat cost O(pages × frames) per refresh; upgrade path: build the list only while the menu is open.

**D11. Export.** Exports the open page; `handoff/` stays at the root; `lastExport` lives in that page's manifest, so `handoff_status` is per page and its result carries `page`. `IMPLEMENT.md` gains a page line (id and title as fields) and its MCP-unavailable instructions name `.cursor-design/pages/<id>/artboards/`; the skill says to check the handoff's page before implementing. Otherwise the format is unchanged; the snapshot is updated.

**D12. Watcher unchanged** (`.cursor-design/**`, 200 ms debounce). Each refresh re-reads `project.json`, so an Agent `open_page`, a page made elsewhere, or a save on another page (its last-edited time) reaches the panel. A save on a page not on stage re-posts identical frames, which changes nothing.

**D13. Zero new dependencies.**

## Error surfaces (rule 06)

| Code | When | Agent hint / panel copy |
|---|---|---|
| `PAGE_NOT_FOUND` | `open_page` names no page; a page-scoped write finds no `pages/<id>/` | Agent: call list_pages. Panel: "That page no longer exists." |
| `CORRUPT_PROJECT` | `project.json` unparsable | Fix it, or delete it to rebuild the list (titles reset). |
| `UNSUPPORTED_PROJECT_VERSION` | `project.json` version is not 1 | As the other `UNSUPPORTED_*_VERSION` codes. |
| `MIGRATION_CONFLICT` | a legacy entry exists in the root and in `pages/page-1/` | Names both paths; move one by hand. |
| `INVALID_ARGS` | malformed `pageId`, title empty / too long / control chars, `MAX_PAGES` reached, last page delete | Existing code, new messages. |
| `COMMENT_NOT_FOUND` | as today; names the page id when the comment is on another page (D7) | Existing code. |

Panel copy goes through `panelRequestCopy.ts` as today. New codes reach the skill in the step that adds them (`agentSkill.test.ts` requires every `code` in `errors.ts` to appear in it).
